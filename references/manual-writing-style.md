# 中文使用手册写作规范

这份规范只服务一件事：**把事实草稿改写成国内成熟 SaaS 产品帮助中心那样的中文**。

它不负责决定写什么——写什么由事实草稿决定。它只负责怎么写。

---

## 零、不可逾越的边界

自然化阶段**只能改**：句式、语序、冗余表达、翻译腔、AI 套话。

**不能改**：事实、UI 名称、操作顺序、页面行为、截图引用、数字与单位。

一句话判据：**改完之后，如果读者照着做会得到不同的结果，那就是改错了。**

不要因为"这样更通顺"就补一句原草稿里没有的说明。手册的可信度来自每一句都能对上真实页面。缺内容是可见的缺口，编内容是看不见的陷阱。

---

## 一、受保护内容：一个字都不许动

以下内容是从真实页面和项目模型里来的事实数据，属于**原文引用**，不是待润色的文案：

| 类别 | 例子 |
|---|---|
| 按钮名称 | 「发送」「新对话」「保存」 |
| 菜单 / Tab 名称 | 「设置」「消息记录」 |
| 页面标题 | 工作台、会员计划 |
| 表单字段名 | 账号、手机号、验证码 |
| Placeholder 原文 | 请输入你的问题 |
| 错误提示原文 | 登录已过期，请重新登录 |
| 路由 | `/chat`、`/artifact/:id` |
| 文件名 / 路径 | `images/annotated/chat.png` |
| 数字与单位 | 1440×900、2 倍图、50 MB |

### 典型错误

真实按钮是「新对话」：

- ✗ 「开启新会话」—— 改了 UI 原文，用户在页面上找不到这个按钮
- ✗ 「新建对话」—— 同上，差一个字也是错的
- ✓ 「新对话」

### 用「」的前提

**只对页面模型里确实记录了的 UI 名称使用「」。**

不确定真实按钮叫什么，就用描述性说法，别硬套书名号：

- ✓ 发送消息（模型里没有按钮原文时）
- ✗ 点击「发送」（模型里没这个词，这是编的）

想让手册里出现真实按钮名，应该在 `manual describe` 阶段把它写进 `detectedActions`，而不是在润色阶段补。

## 二、基本语感

### 简体中文，短句优先

一句话说一件事。超过 40 字就考虑断开。

- ✗ 在完成内容输入之后，用户可以通过点击页面右下角的发送按钮来将当前的请求提交给系统进行处理。
- ✓ 输入完成后，点击「发送」。

### 操作说明直接上动词

操作步骤的主语就是读者，不用点出来。

优先使用这些动词：**点击、选择、输入、打开、返回、上传、下载、查看、保存、删除、切换、展开、收起**。

- ✗ 用户可以点击「发送」按钮以提交当前请求。
- ✓ 点击「发送」提交请求。

### 陈述事实，不做承诺

帮助中心是说明书，不是宣传页。

- ✗ 这项功能能够显著提升你的工作效率。
- ✓ 会话记录保留最近 30 天。

## 三、必须避免的表达

### 翻译腔

| 不要 | 改成 |
|---|---|
| 用户可以点击……以实现…… | 点击…… |
| 通过该功能，用户能够…… | （直接说这个功能做什么） |
| 对……进行……操作 | 直接用动词 |
| 在……的情况下 | ……时 |
| 该页面提供了……的能力 | 这个页面可以…… |
| 出于……的目的 | 为了…… |

### AI 套话

这些词出现即删，几乎没有例外：

`值得注意的是` · `需要注意的是` · `从而提升` · `进一步提升` · `更好地` · `高效地` · `轻松地` · `即可实现` · `助力` · `赋能` · `一站式` · `全方位` · `极大地` · `显著地`

### 机械结构

- ✗ 首先……其次……最后……
- ✓ 用有序列表，或者直接按顺序陈述

段落开头不要排比式的"首先/其次/另外/此外"。需要顺序就用列表。

### 不必要的"您可以"

中文技术文档里"您"大量出现会显得生硬且有距离感。

- ✗ 您可以在此页面查看您的账户信息。
- ✓ 这个页面显示账户信息。

需要指向读者时用"你"，且尽量少用。

### 不必要的解释

不要为显而易见的事加注解。

- ✗ 点击「保存」按钮，即可保存当前的修改内容。
- ✓ 点击「保存」。

## 四、改写对照

| 不推荐 | 推荐 |
|---|---|
| 用户可以点击「发送」按钮以提交当前请求。 | 输入完成后，点击「发送」。 |
| 通过该功能，用户能够快速创建新的对话。 | 点击「新对话」创建会话。 |
| 该页面为用户提供了查看个人资料的能力。 | 这个页面显示个人资料。 |
| 值得注意的是，上传的文件大小不能超过 50 MB。 | 单个文件不超过 50 MB。 |
| 首先输入账号，其次输入密码，最后点击登录。 | 1. 输入账号<br>2. 输入密码<br>3. 点击「登录」 |
| 用户可以通过该入口高效地管理自己的会话。 | 在这里管理会话。 |
| 点击后系统将会自动为您完成相关处理。 | 点击后自动处理。 |

## 五、文档结构：按帮助中心的读法写

参照飞书、钉钉、Notion 等帮助中心：读者带着“我要做成某件事”来，扫一眼标题判断是不是这篇，看前提确认能不能做，照步骤做完，再确认做成了没有。文档里只放帮读者完成这件事的内容。

### 任务指南（主要形态）

程序按下面的顺序渲染，标题文字由模板固定：

| 部分 | 内容 | 由谁决定 |
|---|---|---|
| 标题 | 动宾结构，写读者要完成的结果：「创建出题任务」「查看积分明细」；不写「出题功能介绍」 | 任务模型 `title` |
| 导语 | 一到两句：这件事能帮读者做成什么、什么场景下用。不复述标题 | 文案块 `intro` |
| 前提条件 | 读者能事先判断的条件：账号权限、需要准备的素材或数据。不写“认证有效”这类读者无法判断的执行条件 | `readerPreconditions` |
| 操作步骤 | 首行给出入口链接；之后一步一个可见动作，配图紧跟在相关步骤下 | 动作句由程序生成；补充说明是文案块 `step.<id>` |
| 如何确认已完成 | 「完成标志」写界面上能看到的结果；「预期结果」写证据未覆盖的结果；「请确认以下内容」列读者需自己核对的业务结果 | 完成声明与 `readerChecks` |
| 常见问题 | 每条一个读者会遇到的情况（加粗）加处理办法 | `branches` |
| 相关文档 | 相关任务的链接 | `relatedTasks` |

### 文案块怎么写

- **导语**：说结果和场景，不说界面。✓「用教案生成技能，根据课题和年级生成一份教案初稿。」✗「本文介绍如何使用技能功能。」
- **步骤补充说明**：动作句已经写了“点击「发送」”，补充说明只写读者还需要知道的：输入什么（给可替换的示例或格式）、点了之后会发生什么、要等多久（仅限有证据时）。不要重复动作句。
- 首步入口是没有文字的图标时，补充说明写“入口图标位于……。”，程序会把位置放到动作前面。
- 需要先判断再操作时，以“选择前，确认……。”开头，程序会排成“确认……，再点击……”。

### 不写进正文的内容

读者不关心手册是怎么生成的。下面这些属于维护信息，留在事实包、`review-task` 和发布记录里：

- 截图时间、证据来源、“根据源码推断”“已在浏览器中验证”之类的说明
- 哪些步骤实际执行过、验证范围、“此操作未执行”
- 内部 id、路由参数、测试账号与测试数据

### 页面功能介绍（辅助形态）

页面文档回答“这个页面能做什么”，是任务指南的入口：标题用页面真实名称，导语一两句说清用途，接入口链接和截图，再用二级标题列出主要操作，每项一两句并链接到对应的任务指南。不写“概述”“简介”“总结”这类空壳标题。

## 六、定稿前自查

- [ ] 所有「」里的内容和真实 UI 一字不差
- [ ] 图片路径没动过
- [ ] 操作步骤的数量和顺序没变
- [ ] 没有新增草稿里不存在的功能、按钮、限制
- [ ] 没有编造响应时间、异常行为、业务规则
- [ ] 通读一遍不像机器写的，也不像营销文案
- [ ] 第三节的禁用词一个都没有
- [ ] 导语说的是读者能做成什么，不是“本文介绍……”
- [ ] 没有把截图时间、验证范围、内部 id 写进正文

## 七、通过 Runtime 交接文案

`manual generate <目标>` 需要文案时会停在 waiting_input，并在 `.manual/runs/<runId>/model/<requestId>.request.json` 写出请求：

- `files`：允许读取的文件及其 sha256（草稿、事实包、本规范）。只读这些文件，不要翻整个仓库。
- `facts.copyBlocks`：可填写的文案块及默认文字；`output.allowedBlocks` 之外的键一律被拒绝。
- `limits`：单块最多字数、响应总大小。

响应写成 JSON 后，用 `resume` 提交并继续：

```json
{ "requestId": "<请求里的 requestId>", "inputHash": "<请求里的 inputHash>", "output": { "copy": { "intro": "……", "step.open-editor": "……" } } }
```

```bash
manual resume <runId> --request <requestId> --input <响应.json>
```

- requestId / inputHash 必须原样抄回；事实在等待期间变了（重新采集、改了任务），旧响应会被拒绝（run-input-changed），按提示 `resume --replan`。
- 文案只能改说法：否定或改写受保护的动作、UI 名称会被直接拒绝；新出现的数字、单位或业务承诺需要人工确认（review-required）。
- 页面语义分析（`kind: analyze`）的响应是 `{ "output": { "title": "…", "purpose": "…", "detectedActions": ["…"] } }`，只能填这三个字段；结果标记为模型推断，不等于浏览器验证。
- 同一份响应重复提交是幂等的；请求与响应可能含业务文案，保存在本地 `runs/` 下，不入库。

### 块标记与人工补充

正式文档中的 `<!-- manual:block id=… -->` … `<!-- /manual:block -->` 由程序生成，用来在更新时定位生成内容：

- 文案块（`intro`、`step.<id>`）里**不要**写 HTML 注释、标题、图片或列表——`validateCopy` 会拒绝（`structure-in-copy`）。
- 需要长期保留的人工说明写在块**之外**（两个块之间），`generate` / `update` 会原样保留；
  想接管某个生成块时把块头改为 `<!-- manual:block id=… owner=human -->`，之后生成器不再覆盖它。
- 数据来自 Fixture 模拟时，文档会写明"数据来源：界面状态由测试数据模拟"，改写时不能删掉或弱化这句说明。
