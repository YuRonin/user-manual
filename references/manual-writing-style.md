# 中文使用手册写作规范

这份规范决定手册**怎么写**：读起来像产品团队里熟悉这个功能的同事，坐在读者旁边一边指着屏幕一边讲。写什么由事实决定（页面模型、任务模型、事实包、截图），这里不新增事实。

它约束所有读者能看到的文字：

| 写在哪里 | 谁来写 | 对应本规范 |
|---|---|---|
| 页面 `purpose`、`guide[].title` / `guide[].instruction` | `manual describe` 时读源码后写 | 第三节“页面指南” |
| 任务模型的 `title`、步骤 `instruction`、`readerPreconditions`、完成声明、`readerChecks`、`branches`、`capture.readerCaption` | 建模任务时写 | 第三节、第五节 |
| 文案块 `intro`、`step.<id>` | `generate` 停下等文案时写 | 第三节、第七节 |

---

## 零、不可逾越的边界

一句话判据：**读者照着做，结果和真实页面一致。**

- 可以改：句式、语序、详略、衔接、冗余表达、翻译腔、套话。
- 不能改：UI 名称、操作顺序、页面行为、截图引用、数字与单位、完成条件。
- 不能补：源码和截图里没有的功能、按钮、限制、耗时、业务规则、保证。

写得详细不等于写得多。详细是把读者需要、而事实里确实有的信息说出来；没有依据的句子一句都不加。缺内容是可见的缺口，编内容是看不见的陷阱。

## 一、受保护内容与「」的用法

### 受保护内容：一个字都不许动

| 类别 | 例子 |
|---|---|
| 按钮、菜单、Tab、选项名称 | 「发送」「新对话」「保存草稿」 |
| 页面标题 | 工作台、会员计划 |
| 表单字段、Placeholder、错误提示原文 | 活动标题、搜索我的文件、登录已过期，请重新登录 |
| 路由、文件名、路径 | `/chat`、`images/annotated/chat.png` |
| 数字与单位 | 1440×900、10 道题、50 MB |

真实按钮是「新对话」，写成「开启新会话」「新建对话」都是错的，读者在页面上找不到。

### 「」只给读者要找到并操作的控件

「」是程序识别 UI 原文的标记：提交时，「」里的每个名称都必须在事实里出现过，否则整份文案被拒绝。它也是读者眼里的“去页面上找这几个字”。用多了，正文变成一串标签，读者反而抓不住重点。

**加「」：** 读者要点击、选择、打开、切换的那个控件——按钮、菜单项、Tab、链接、单选或下拉选项。

**不加「」，写成普通文字：**

- 表单字段：“修改活动标题、开始时间和结束时间”，不写“在「活动标题」「开始时间」「结束时间」中修改”。
- 位置和区域：“在左侧会话列表里”“在新对话页的推荐区”；区域标题是读者唯一的定位线索时，可以引一次。
- 功能和概念：技能、云盘、积分、教案卡片。
- 示例输入：用中文双引号，“请为二年级数学设计一节 40 分钟的教学活动”。
- 标题：任务标题、页面标题、指南小标题都不用「」。

**数量：** 同一段里同一个名称只在第一次加「」；不要连写三个以上「」；动作句已经写了“点击「发送」”，补充说明再提到它直接写“发送后……”。

不确定按钮的真实名称时，用描述性说法（“点击输入框右下角的发送按钮”），不要猜一个名字放进「」。想让真实名称出现在手册里，在 `manual describe` 阶段把它写进 `detectedActions` 或 `guide`。

| 不推荐 | 推荐 |
|---|---|
| 在「我的活动」中点击草稿的「继续编辑」进入详情。在「活动标题」「开始时间」「结束时间」中修改后，点击「保存草稿」。 | 在我的活动列表里找到草稿，点击「继续编辑」进入详情。修改活动标题、开始时间和结束时间后，点击「保存草稿」，改动会保留在草稿里，学生暂时看不到。 |
| 在技能搜索框输入「教案生成」。确认搜索结果是「教案生成」，再点击「教案生成」。 | 在技能搜索框输入“教案生成”，下方出现同名技能后点击「教案生成」。 |
| 从「我要出题」生成一份练习题 | 用“我要出题”快速生成练习题 |

（最后一行是标题：标题不用「」；第三列里“保留在草稿里，学生暂时看不到”这类后果，只有源码里能看到草稿和发布的区别时才写。）

## 二、手册语气

### 读者是谁

读者是第一次用这个功能的普通用户：知道自己想做成什么事，不知道入口在哪、每个选项是什么意思、点了之后会怎样。读者不关心手册是怎么生成的，也不懂内部术语。

### 口吻

- **像同事讲解，不像说明书条文，也不像宣传页。** 平实、具体、友好，不夸、不吓人。
- **主语是读者时省略主语。** 需要指向读者时用“你”，不用“您”，一段里最多一两次。
- **陈述页面上真实发生的事。** “点击后，右侧打开题目预览”，不写“系统将为您智能生成”。
- **先说结果和用途，再说操作。** 读者先知道“为什么做这一步”，再看“怎么做”。
- **句子长短跟着意思走。** 一句一件事是常态；需要交代“先……再……，……后会……”的顺序和因果时，用一个完整的长句，不要拆成碎片。
- **一节只讲一件事。** 宁可多分几节，也不要用分号把三件事串成一段。

### 参照范文

语气和详略参照优秀的产品帮助文档，以一篇《上传本地文件》为例，值得学的是这几点：

- **开头先交代用处。** 一两句说这项功能覆盖什么、对你有什么用，再进入操作。
- **按“做成这件事的几种方式”分节。** 上传文件分成本地上传、剪贴板上传、拖拽上传、添加网页链接，每节标题就是那种方式。
- **每节两三句：什么情况下 → 怎么做 → 你会看到什么。** “本地的资源可以多选文件再拖拽到网站窗口，看到「拖放文件以上传」的提示，松开鼠标自动开始上传。”
- **说出省掉了什么麻烦。** “在设计工具中复制图片后可以直接粘贴，无需导出文件再上传。”前提是两种做法在产品里都真实存在。
- **限制紧跟在相关句后，用括号补一句。** “支持常见视频格式如 MP4、WebM（能否播放还取决于浏览器支持）。”
- **「」一段一两处，从不连写。**

不照搬的：“强大的”“完美显示”“更省心”这类评价词，以及“即将支持”这类没有事实依据的计划。

### 优先使用的动词

**点击、选择、输入、打开、返回、上传、下载、查看、保存、删除、切换、展开、收起、拖动、勾选**。

| 不推荐 | 推荐 |
|---|---|
| 用户可以点击「发送」按钮以提交当前请求。 | 写好问题后，点击「发送」。 |
| 您可以在此页面查看您的账户信息。 | 这个页面显示你的账号信息和会员状态。 |
| 这项功能能够显著提升你的工作效率。 | 会话记录按时间分组，可以搜索标题找到以前的对话。 |

## 三、写得够详细：每一处该写什么

手册太简短，最常见的原因不是写得啰嗦被删了，而是**只复述了动作，没有回答读者的下一个问题**。动作句“点击「发送」”程序已经生成；文字要补的是读者照做时心里会问的那几句：

1. **这是干什么用的？什么时候需要它？**
2. **要填什么、选哪个？各个选项有什么区别？**
3. **点了之后会看到什么？下一步去哪？**
4. **有什么要先确认、做了就不能撤回的地方？**

每个问题只在事实里有答案时才写。答案的来源按可信度：浏览器采集到的截图与断言 > 页面源码里的文案、选项、确认弹窗、空状态、禁用条件 > 页面模型的 `purpose` 和 `detectedActions`。源码里看到“删除后不能恢复”的确认弹窗，就可以写；源码里看不出要等多久，就不写耗时。

### 导语（`intro`、页面 `purpose`）

一两句：这里能做成什么、对你有什么用。不复述标题，不写“本文介绍……”。

| 偏短 | 推荐 |
|---|---|
| 与 AI 对话并使用技能处理教学任务、附件和生成产物。 | 在这里直接向 AI 提问，也可以附上资料、选择教学技能，让它帮你出题、写教案。生成的题目和教案会以卡片形式出现在对话里。 |
| 选择实际可用的「教案生成」技能，提交教学需求并查看回复。 | 想让 AI 按固定格式写教案，就用教案生成技能：说清课题、年级和课时，它会在对话里给出一份教案初稿。 |

### 页面指南（`guide[].instruction`）

每条两三句，大约五十到一百二十字：什么情况下用 → 怎么做 → 你会看到什么；有依据的限制放在括号里跟在后面。超出这个长度，通常说明一节塞了两件事，拆成两节。小标题写读者要做的事，越短越好：“更换题目”“剪贴板上传”。

| 偏短 | 推荐 |
|---|---|
| 在左侧点击「新对话」，进入空白会话。 | 想换个话题时，点击左侧栏顶部的「新对话」。之前的对话会留在左侧列表里，随时可以回去接着聊。 |
| 打开「技能与组合技」并选择「技能」，搜索实际可用的技能。 | 技能是为教学场景预设好的能力，比如出题、写教案。点击输入框左下角的「技能与组合技」，切换到技能，搜索并选中需要的那个，输入框里就会出现它的标签。 |

| 一段塞了三件事 | 拆开写 |
|---|---|
| 确认无误后点击「发布活动」；发布后题目和公布方式不能再改。不再需要的草稿可以点击「删除活动」，删除后不能恢复。 | **发布活动**：确认无误后点击「发布活动」，在确认框里点击「确认发布」。（发布后，题目和答案公布方式都不能再改。）<br>**删除草稿**：不再需要的草稿，点击「删除活动」并确认。删除后它不会再出现在活动列表里，也不能恢复。 |

（推荐列里的“随时可以回去接着聊”“输入框里出现标签”必须能在源码或截图里找到对应，找不到就删掉这半句。）

### 步骤说明（任务步骤 `instruction`、文案块 `step.<id>`）

动作句程序已经写了，说明只写动作句没说的：位置（首步必写）、输入什么（给可替换的示例或格式）、选项区别、点了之后界面怎么变。一到三句。

| 偏短或重复 | 推荐 |
|---|---|
| 输入资料名称或相关关键词。 | 输入文件名中的关键词即可，不需要完整文件名；列表会随输入即时筛选。 |
| 提交后等待助手回复。 | 发送后，回复会在当前对话中逐段出现；题目生成完成时，回复下方出现题目卡片。 |

需要先判断再操作时，以“选择前，确认……。”开头，程序会排成“确认……，再点击……”。首步入口是没有文字的图标时，写“入口图标位于……。”，程序会把位置放到动作前面。

### 前提条件（`readerPreconditions`）

写读者自己能判断、能提前准备的事：账号权限、会员等级、要准备的文件或数据。不写“已登录且认证有效”这类执行条件，最多写“已登录 NeoAgent”。

### 完成确认（完成声明、`readerChecks`）

写读者在界面上能看见的结果，以及还需要自己核对的业务内容。“助手回复已出现”之外，告诉读者核对什么：“打开题目卡，核对题目数量和年级是否与需求一致”。

### 常见问题（`branches`）

`condition` 写读者看到的情况，用读者的话（“搜索不到想要的技能”），不写内部状态。`effect` 写原因（有依据时）和具体处理办法。不要写给维护者看的话，例如“不要把点击发送当成完成”“不能把任务记为完成”。

| 写给维护者 | 写给读者 |
|---|---|
| 不要把点击发送当成完成；先核对当前会话，仍无结果时保留会话信息并反馈。 | 回复可能还在生成，先留在当前对话等待；刷新后仍没有回复，记下对话标题并联系客服。 |

### 截图说明（`capture.readerCaption`）

一句话说清这张图是操作前还是操作后、读者该看图上的哪里。

## 四、要删改的表达

下面的模式来自中文改写里常见的问题。它们是检查线索，不是见词就删：先看这句话在上下文里是不是空泛、重复或让读者误解，再动手。其中标 ⚙ 的几条程序会自动检查，文案块和页面 guide 命中会被拒绝，任务模型命中会出现在 `review-task` 警告里。

### 套话与拔高 ⚙

这些词在手册里几乎没有正当用途，出现即删：

`值得注意的是` · `需要注意的是` · `从而提升` · `进一步提升` · `更好地` · `高效地` · `轻松地` · `即可实现` · `助力` · `赋能` · `一站式` · `全方位` · `极大地` · `显著地` · `无缝` · `深入探讨` · `至关重要` · `总而言之` · `综上所述` · `希望对你有帮助`

同类但需要看上下文的：

- **假对比**：“这不仅是一个按钮，更是高效备课的入口。”→ 直接说按钮做什么。
- **意义拔高与句尾赞美**：“……彰显了产品对教师的关怀。”→ 删掉尾巴，保留事实。
- **起跑式铺垫**：“接下来让我们看看如何……”“以下是你需要知道的”→ 删掉，直接开始。
- **客服腔**：“好的！”“希望对你有帮助！”→ 删掉。
- **首句复读标题**：标题“更换题目”，正文第一句“本节介绍如何更换题目”→ 删掉。
- **套话收尾**：“快去试试吧！”“让教学更轻松”→ 删掉。

### 翻译腔与书面腔

| 不要 | 改成 |
|---|---|
| 用户可以点击……以实现…… | 点击……，…… |
| 通过该功能，用户能够…… | （直接说这个功能做什么） |
| 对……进行……操作 | 直接用动词：“对文件进行删除”→“删除文件” |
| 在……的情况下 | ……时 |
| 该页面提供了……的能力 | 这个页面可以…… |
| 出于……的目的 | 为了…… |
| 被系统自动保存 | 会自动保存（仅在源码确认时） |
| 一个用于管理历史的会话的列表 | 会话列表 |

### 称呼 ⚙

不用“您”。需要指向读者用“你”，能省略就省略。

### 「」堆叠 ⚙

见第一节：连写三个以上「」、同一段重复引同一个名称，都会被拦下。

### 机械结构

- 段落开头不用“首先……其次……最后……”排比；有顺序就交给编号步骤，或者用“先……再……”。
- 不要把一段连贯的说明拆成很多单句碎片，也不要为了显得简短把因果关系删掉。
- 不用破折号制造悬念；不用粗体装饰普通句子（常见问题的情况标题由程序加粗）。
- 不用表情符号、感叹号。

### 维护信息混入正文

读者不关心手册是怎么生成的。下面这些属于维护信息，留在事实包、`review-task` 和发布记录里：

- 截图时间、证据来源、“根据源码推断”“已在浏览器中验证”
- 哪些步骤实际执行过、验证范围、“此操作未执行”“认证有效”
- 内部 id、路由参数、选择器、测试账号与测试数据
- 写给维护者的判断：“不能记为完成”“截图中的题目是采集示例”（需要提醒读者截图是示例时，写“截图中的内容仅作示意，以你实际生成的为准”）

## 五、文档结构：按帮助中心的读法写

参照飞书、钉钉、Notion 等帮助中心：读者带着“我要做成某件事”来，扫一眼标题判断是不是这篇，看前提确认能不能做，照步骤做完，再确认做成了没有。

### 任务指南（主要形态）

程序按下面的顺序渲染，标题文字由模板固定：

| 部分 | 内容 | 由谁决定 |
|---|---|---|
| 标题 | 动宾结构，写读者要完成的结果：“创建出题任务”“查看积分明细”；不写“出题功能介绍”，不用「」 | 任务模型 `title` |
| 导语 | 一两句：能做成什么、对你有什么用 | 文案块 `intro` |
| 前提条件 | 读者能事先判断的条件：账号权限、需要准备的素材或数据 | `readerPreconditions` |
| 操作步骤 | 首行给出入口链接；之后一步一个可见动作，配图紧跟在相关步骤下 | 动作句由程序生成；补充说明是文案块 `step.<id>` |
| 如何确认已完成 | “完成标志”写界面上能看到的结果；“预期结果”写证据未覆盖的结果；“请确认以下内容”列读者需自己核对的业务结果 | 完成声明与 `readerChecks` |
| 常见问题 | 每条一个读者会遇到的情况（加粗）加原因和处理办法 | `branches` |
| 相关文档 | 相关任务的链接 | `relatedTasks` |

### 页面功能介绍（辅助形态）

页面文档回答“这个页面能做什么”，是任务指南的入口：标题用页面真实名称，导语一两句说清用途，接入口链接和截图，再按 `guide` 列出主要操作，每项两三句（见第三节），一项只讲一件事，能对应到任务指南时附上链接。不写“概述”“简介”“总结”这类空壳标题。

## 六、定稿前自查

事实（优先于一切风格要求）：

- [ ] 所有「」里的内容和真实 UI 一字不差
- [ ] 图片路径、步骤数量和顺序没动过
- [ ] 每一句新增的说明都能在源码、截图或事实包里找到依据
- [ ] 没有编造耗时、数量、限制、业务规则和保证

## 七、通过 Runtime 交接文案

`manual generate <目标>` 需要文案时会停在 waiting_input，并在 `.manual/runs/<runId>/model/<requestId>.request.json` 写出请求：

- `files`：允许读取的文件及其 sha256（草稿、事实包、本规范）。写导语和步骤说明需要更多背景时，可以回看页面模型（`.manual/pages/<id>.yaml`）和其中列出的源码，但只用来理解已有事实，不从中添加新功能或新数字。
- `facts.copyBlocks`：可填写的文案块及默认文字；`output.allowedBlocks` 之外的键一律被拒绝。默认文字通常偏短，按第三节补全，不要原样交回。
- `limits`：单块最多字数、响应总大小。

响应写成 JSON 后，用 `resume` 提交并继续：

```json
{ "requestId": "<请求里的 requestId>", "inputHash": "<请求里的 inputHash>", "output": { "copy": { "intro": "……", "step.open-editor": "……" } } }
```

```bash
manual resume <runId> --request <requestId> --input <响应.json>
```

- requestId / inputHash 必须原样抄回；事实在等待期间变了（重新采集、改了任务），旧响应会被拒绝（run-input-changed），按提示 `resume --replan`。
- 文案只能改说法：否定或改写受保护的动作、UI 名称会被直接拒绝；第四节标 ⚙ 的风格问题也会被拒绝（`style-*`），改完重交即可；新出现的数字、单位或业务承诺需要人工确认（review-required）。
- 页面语义分析（`kind: analyze`）的响应是 `{ "output": { "title": "…", "purpose": "…", "detectedActions": ["…"] } }`，只能填这三个字段；结果标记为模型推断，不等于浏览器验证。`purpose` 按第三节导语的要求写。
- 同一份响应重复提交是幂等的；请求与响应可能含业务文案，保存在本地 `runs/` 下，不入库。

### 块标记与人工补充

正式文档中的 `<!-- manual:block id=… -->` … `<!-- /manual:block -->` 由程序生成，用来在更新时定位生成内容：

- 文案块（`intro`、`step.<id>`）里**不要**写 HTML 注释、标题、图片或列表——`validateCopy` 会拒绝（`structure-in-copy`）。
- 需要长期保留的人工说明写在块**之外**（两个块之间），`generate` / `update` 会原样保留；
  想接管某个生成块时把块头改为 `<!-- manual:block id=… owner=human -->`，之后生成器不再覆盖它。
- 数据来自 Fixture 模拟时，文档会写明"数据来源：界面状态由测试数据模拟"，改写时不能删掉或弱化这句说明。
