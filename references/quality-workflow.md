# 可用手册的验收与实践

## 页面与任务

页面不是按钮清单。通过 describe 的 guide 数组记录具体操作，每项含 id、title、instruction，可选 target（真实可见控件）和 taskId（已发布任务）。最多选择五个关键 target；页面截图编号与说明顺序对应。说明应包含入口、输入要求、结果与空状态。没有 guide 时仅作为总览，不能声称完整教程。

任务 instruction 中的按钮名必须与实际 UI 一致。动作句由结构化 action 生成；补充说明解释目的、输入和结果，避免重复动作句。若首步入口是无可见文字的图标，可在 instruction 写“入口图标位于……。”；生成器把这类简短位置说明放到动作前。每个关键转折或最终结果都应声明 capture；标号对应任务步骤号。完成声明必须绑定界面断言，不用 URL 相同来证明业务完成。完成断言仅覆盖部分目标时，在 `completion.readerChecks` 列出读者还需自行核对的项目；模板把它们单列在“请确认以下内容”下，不提升为“完成标志”。
正式手册面向读者：正文写可见入口、具体动作、完成时应看到的内容和异常处理。证据来源、是否单独采集等维护信息留在事实包与质量记录中，不写进读者遇到问题的说明。生成模板用“完成标志：”写界面已观察到的结果，用“预期结果：”写证据未覆盖的结果；步骤是否实际执行、验证范围等信息只出现在 `review-task` 与发布记录中，不进入正文。

## 先检查数据与页面

新建任务、改过定位或数据前提不确定时，执行 manual plan-capture <id> --live 做真实只读预演；仅检查到写操作前，不发布截图或修改任务证据。已有新鲜采集证据的重复生成可跳过这一步。`preconditions` 保留采集所需条件；若其中有「会话认证有效」「列表中可搜索到结果」等不适合要求读者事先判断的条件，可另写 `readerPreconditions` 作为手册中的简明前提，不改变执行审批范围。`step.requires` 用可执行断言检查实际数据。例如技能结果可见、输入框可编辑。前提不满足时报告缺少什么，不猜测第一个结果、不盲目重试。

跨页动作声明 pageAfter，stateAfter 引用目的页状态；未显式指定后置状态时，相邻步骤切页可推断目的页。优先使用 role/name、label 或 testId；必要时用 within 限定范围。alternatives 只能填写已观察到的同一控件的替代定位，不允许宽泛 first-child。回退定位会留下记录，在线验证把它报告为不确定，供维护者修正。

## 已授权测试写操作

默认 write 停止，destructive 不执行。用户已授权测试实践且需要验证提交结果时，在登记的非生产 environment 中配置 task.writeAuthorization：origin、steps（精确步骤 id）、expiresAt、decisionRef（现有用户授权依据，不含凭证）。环境在 config.fixtures.environments 登记 origins。授权字段参与任务审批，运行时检查当前 origin 和有效期。

获授权的 write 采集不自动重试。出现 outcome-unknown 后，先检查现有结果；不要重新生成导致重复提交。plan-capture --live 和 verify --live 始终只执行安全步骤。授权到期不会影响已发布证据，但禁止再次写入。

Run 因 `auth-expired`、`auth-missing` 或 `login-required` 停下时，可执行 `manual auth login --resume <Run ID>`（指定档案时加 `--profile <名称>`）。命令先核对 Run 的等待原因与档案；交互登录成功并把状态保存到用户级私有缓存后，自动继续原 Run。认证值不会进入项目产物。若只想保存登录状态，仍可单独运行 `manual auth login`。

如果已提交的结果存在，而最后状态断言或截图失败，先修正不稳定的界面断言并重新批准变更后的任务范围。用 `manual capture-task <id> --reconcile-url <已有会话URL> --prior-captures <此前截图ID, ...>` 只读核对该会话并补采最终截图。此命令要求提交前截图完整、任务定义与场景一致，并在既有会话中找到本次输入和完成状态；它不会重复任何任务动作。核对成功后运行 `manual generate task:<id> --offline`，避免重新提交。

如果提交与截图都已验证，只是手册目标还缺少最后一步查看结果，可在任务末尾新增一个带界面断言和 after 截图的 `read` / `local` 步骤，重新批准后运行 `manual capture-task <id> --continue-url <已有会话URL>`。此模式要求原步骤和 Capture 链未变、最后已验证步骤为提交、同一会话中能看到原输入与结果；只执行新增的查看动作，不重放提交。随后离线生成并检查截图、完成声明与读者核对项。完整会话 URL 只用于本次命令，不要写入项目文件或测试报告。
如果只修改了手册说明，而原采集已经包含最后的查看步骤，也可对同一个会话使用 `--continue-url` 只读刷新最后一步。此时工具还会检查页面断言版本、场景版本、原动作和 Capture 链；任一变化都拒绝复用。刷新只重新执行最后的查看动作，原提交步骤不执行。

## 异常恢复

- **`outcome-unknown`（写操作结果不明）**：不要重新生成或重试提交。先在已有会话中检查结果，再按上一节用 `capture-task --reconcile-url` 核对，或用 `--continue-url` 续采只读的结果查看步骤。
- **`--offline` 因 `identityRevision` 变化拒绝复用证据**：说明登录身份变了。不要绕过身份隔离；只改文案时可用 `manual generate-task <id>` 对任务现有证据重新生成草稿并通过定稿门槛；需要当前身份的证据时，先 `--plan` 给用户审阅，再重新采集。
- **登录失效**：`manual auth login --resume <runId>`；单独排查时运行 `manual auth check --path <受保护页面路径> --json`。`auth status` 只说明缓存存在，不说明仍然有效。

## 图片、验证和交付

交付前逐篇按读者的实际任务审阅，而不是仅以 Runtime 发布成功为准：

任务事实文件中的 `factPack.quality.checks` 给出入口地址、第一步控件位置、前提、步骤、完成断言、异常分支和截图七项初筛，`warnings` 指出缺口；这是模型与证据的静态检查，不能证明读者能完成任务。`completionClaimsVerified` 只说明已声明断言通过，仍须按任务目标审阅是否还缺业务结果。第一步的位置要按实际界面核对；仅写“点击某按钮”可能不足以找到图标入口。截图缺失只针对声明 `capture` 且实际执行的步骤；简单导航可不逐步配图，但关键转折与结果图仍需人工检查。人工补充写在生成块外时，还要审阅最终 Markdown，并在发布流程中重新定稿，以便发布记录包含这段文字。首次阅读者测试需单独记录完成率和卡点，不能用 `verify --artifacts` 代替。基准记录示例见 `docs/archive/QUALITY-BENCHMARK.md`。

1. 标题写清用户要完成的结果；“前提条件”列出真实权限、数据或素材要求。
2. 每步只描述一个可见动作，控件名称与截图一致；相邻两句不能重复同一动作（例如“点击发送”后又写“点击发送”）。
3. 关键输入给出可替换的示例或格式，不把测试数据写成唯一可用内容。
4. 完成标志对应最后一步的界面断言；证据只到提交前时，模板会写成“预期结果”，不要在文案块里改写成已完成。
   规划出现 `completion-before-final-step` 时，检查任务模型里的 claim checkpoint；这是审阅提醒，不代表前一步的结果一定无效。
5. 登录失效、无数据、搜索不到结果等常见分支，至少说明如何返回或检查前提；没有观察到的错误行为不编造。
6. 截图紧跟相关步骤，核对标注位置和可读性；缺关键截图时把文档标为待补证据。

默认流程会等待模型文案。上述检查发现含糊、重复或错误完成声明时，修正任务模型或重写文案块，再交付；用 `--copy-default` 出的粗稿必须经过这轮审阅才能交付。

`manual review-task <task-id> --preview` 可把任务目标、逐步动作、发布图、图注和完成证据集中列出，并生成本地读者预览。`completion.goalChecks` 中每个目标部分用 `claimIds` 关联已有界面声明，或用 `readerChecks` 关联现有读者核对原文；报告会把仍需读者核对的结果明确列出。操作前标注目标与动作目标、截图记录时机会做静态冲突检查；操作后图是否真能说明图注所写结果仍由审阅者看图确认。目标映射与静态通过都不等于业务结果已完成。

只引用 images/annotated 发布图，原图、诊断图与认证缓存始终私有。查看最终发布图：标注是否对应说明、文字是否清楚、遮挡是否覆盖关键区域；正文中的图片本身链接到原尺寸发布图，读者点击即可放大。为每个实际采集的关键步骤在 `capture.readerCaption` 写读者图注，说明图是操作前还是操作后、标注指向什么，以及哪些数字只是示例；图注必须与发布图相符。发送后的回复图只能说明结果，不能当作发送按钮定位图。缺图注会出现 `step-image-caption-unreviewed` 提示。若旧标注把读者导向错误控件，可设置 `capture.readerVisible: false`，保留证据但不把该图放进正文；确保相邻步骤仍有足够的操作与结果图。image-heavily-redacted 提示改用演示数据或局部截图，不删除隐私保护。image-unannotated / step-image-missing 提示补关键图或解释为何无需截图。

verify --artifacts 仅证明文件与事实一致，onlineChecked=false；不能报告业务成功。verify --live 检查当前可回放界面。报告已执行步骤数量、绑定且通过的完成声明，以及停止点。没有绑定断言的业务结果始终是预期。

每次 Runtime 发布会更新 docs.outputDir/index.md 的 manual:catalog 区块（分组默认为操作指南 / 功能介绍，配置 docs.catalog 后按配置；引用了未发布手册时跳过并告警 catalog-unknown-entries），区块外人工文字保留；已有无标记的 index.md 保留并提示。交付时从该入口核对文档、图片与任务链接。

## 本地修改后安装

将已验证的源码安装到实际调用的 skill 目录，保留可恢复备份，不包含 .git 或业务数据；在安装目录执行 npm ci。按客户端安装别名：node bin/install-compat.js --client codex（或 claude / all）。再次实践必须调用安装目录的 bin/manual.js；报告源码与安装副本是否一致。
